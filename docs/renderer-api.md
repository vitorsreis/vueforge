# Renderer API

`createVueforgeRenderer` exposes Vueforge's SSR pipeline without requiring
Express or another HTTP framework. It is intended for custom servers, RPC
adapters, workers, jobs, and test harnesses that want to own the transport.

## Create a renderer

```ts
import { createVueforgeRenderer } from '@vitorsreis/vueforge'

const renderer = await createVueforgeRenderer({
  root: process.cwd(),
  mode: 'development',
  main: 'src/App.vue',
})
```

Options:

| Option   | Description                                                                                                                                           |
| -------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| `root`   | Project directory. Defaults to `process.cwd()`.                                                                                                       |
| `mode`   | Explicit `development` or `production` mode. When omitted, uses config `mode` and then defaults to `production`.                                      |
| `config` | Optional configuration file path relative to `root`. When omitted, `vueforge.config.ts` is loaded when present and the remaining options override it. |

The renderer resolves `main` exactly like the CLI. Development mode uses
Vite's SSR runner and reloads changed modules. Production mode reads the
artifacts generated by `vueforge build`.

Changes to a configured factory are picked up on the next development render.
The last valid factory remains active while an edited module has a temporary
syntax error. Component and style updates use Vite HMR. Changes to transport,
TLS, `vite.server`, the `main` source shape, build output, root, or mode require
restarting the owning process.

The renderer options use the same shape as `VueforgeConfig`, except for
`server` and `tempDir`. They include `root`, `mode`, `main`, `format`,
`origin`, `base`, `document`, `limits`, `build`, and `vite`. Server transport
options such as `server.port`, `server.unix`, and `server.cors` belong to
`vueforge serve`.

```ts
const renderer = await createVueforgeRenderer({
  root: process.cwd(),
  mode: 'development',
  main: 'src/App.vue',
  limits: { renderTimeoutMs: 10_000 },
  vite: { server: { hmr: false } },
})
```

When `mode` is omitted, the renderer uses `mode` from the loaded
`vueforge.config.ts` and falls back to `production`.

When `config` is a path, it is resolved relative to `root` and can be a
JavaScript or TypeScript Vueforge configuration file:

```ts
const renderer = await createVueforgeRenderer({
  root: process.cwd(),
  config: 'config/vueforge.server.ts',
})
```

Top-level renderer options supplied alongside `config` override values loaded
from that file.

For a host that already has the Vue application factory in memory, `main` can
be a handler directly. It receives the complete request context for each
render and an optional runtime descriptor. It returns a fresh Vue app or
`{ app }`:

```ts
import { createSSRApp } from 'vue'
import { createVueforgeRenderer } from '@vitorsreis/vueforge'
import App from './src/App.vue'

const renderer = await createVueforgeRenderer({
  main: (context, runtime) =>
    createSSRApp(App, { ...context.props, runtimeTarget: runtime?.target }),
})
```

## Render a request

Pass the complete application context to `render`:

```ts
const response = await renderer.render({
  context: {
    props: { title: 'Orders' },
    locale: 'pt-BR',
  },
  format: 'json',
})
```

The request options correspond to the controls available on `POST /render`:

| Option        | Description                                                                |
| ------------- | -------------------------------------------------------------------------- |
| `context`     | Required request context passed to the Vue app.                            |
| `template`    | Named catalog entry selected for this render.                              |
| `format`      | `json` or `html`. If omitted, `accept` and project configuration are used. |
| `hydrate`     | Includes the public hydration payload and browser assets.                  |
| `accept`      | Media types used when `format` is omitted.                                 |
| `errorFormat` | `json` or `html` for development render failures.                          |

For a catalog, `template` must be a configured name:

```ts
const response = await renderer.render({
  context: { props: { number: 'A-42' } },
  template: 'invoice',
  format: 'html',
})
```

## Adapt the response

The result is transport-neutral and contains the information a custom server
needs to create its own response:

```ts
{
  status: 200,
  headers: {
    'Content-Type': 'application/json; charset=utf-8',
  },
  body: {
    head: [],
    content: '<h1>Orders</h1>',
  },
}
```

When `format` is `json`, `body` contains `head`, `content`, and an optional
`state`. When `format` is `html`, `body` is the complete document string.

An adapter can map the result to any server API:

```ts
const response = await renderer.render(request)

serverResponse.statusCode = response.status
for (const [name, value] of Object.entries(response.headers)) {
  serverResponse.setHeader(name, value)
}
serverResponse.end(
  typeof response.body === 'string'
    ? response.body
    : JSON.stringify(response.body),
)
```

The renderer does not parse HTTP requests, authenticate callers, apply CORS,
or write to a socket. Those responsibilities remain with the custom adapter.

## Errors

Input, template, timeout, capacity, and output-limit failures return their
corresponding status and a JSON error body. In development, rendering failures
can return normalized file, line, source-frame, and stack information:

```ts
const response = await renderer.render({
  context: {},
  errorFormat: 'json',
})

if (response.status >= 400) {
  console.error(response.body)
}
```

Production component failures remain generic in the returned body. Detailed
component errors are logged by Vueforge.

## Lifecycle

Keep one renderer instance alive and close it when the host process shuts down:

```ts
const renderer = await createVueforgeRenderer({ mode: 'production' })

try {
  // Handle requests with renderer.render(...).
} finally {
  await renderer.close()
}
```

`close` is idempotent. Rendering after the renderer has been closed rejects
with an error. Each render receives an isolated application context, while
compiled modules and production workers are reused by the renderer instance.

## State and hydration

An entry factory can read and update `context.state`. The updated value is
returned in the JSON body:

```ts
const response = await renderer.render({
  context: { state: { count: 4 } },
})
```

Use `hydrate: true` only when the resulting document will be sent to a
browser. The complete context, including state, is public in the
`__VUEFORGE__` script payload.
